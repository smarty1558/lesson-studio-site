# 음악 학원 사이트 제작 위키

## 0. 사이트의 핵심 목적

음악 학원 사이트는 단순히 예쁜 홈페이지가 아니라, 처음 방문한 사람이 신뢰를 느끼고, 수업을 이해하고, 상담 신청까지 하게 만드는 전환형 사이트여야 한다.

핵심 목적은 다음과 같다.

1. 학원의 분위기와 전문성을 빠르게 전달한다.
2. 어떤 수업을 받을 수 있는지 명확히 보여준다.
3. 강사진, 커리큘럼, 수강 결과물을 통해 신뢰를 만든다.
4. 방문자가 상담 신청, 체험 수업 예약, 카카오톡 문의로 이동하게 만든다.
5. 운영자가 수업, 강사, 공지, 후기, 포트폴리오를 쉽게 업데이트할 수 있게 한다.

## 7. 수강료 / 프로그램 페이지

### 7.1 수강료 공개 방식

#### 완전 공개형

- 장점: 투명하고 신뢰감이 높다.
- 단점: 가격 비교만 당할 수 있다.

#### 범위 공개형

- 취미반: 월 00만 원부터
- 입시반: 상담 후 결정
- 프로듀싱 패키지: 과정별 상이

#### 비공개 상담형

- 장점: 상담 전환을 유도할 수 있다.
- 단점: 방문자가 답답해할 수 있다.

### 7.2 추천 방식

처음에는 범위 공개형 + 상담 유도형이 좋다.

- 보컬 취미반: 월 4회 기준
- 작곡 / 미디반: 개인 목표에 따라 상이
- 입시반: 실력 진단 후 커리큘럼 설계
- 원데이 클래스: 별도 안내

### 7.3 프로그램 카드 필드

- 프로그램명
- 대상
- 수업 횟수

## 22. MVP 없이 바로 바이브코딩하는 방식

이 프로젝트는 MVP를 따로 정하지 않는다. 처음부터 최소 기능만 만든다가 아니라, 필요한 기능을 생각나는 대로 계속 추가할 수 있는 운영형 웹서비스로 만든다.

중요한 건 기능을 줄이는 게 아니라, 기능을 추가해도 사이트가 터지지 않도록 처음부터 구조를 잘 나누는 것이다.

### 22.1 개발 방향

- MVP 없음
- 처음부터 전체 기능을 열어둔 구조로 개발
- mock data로 시작 가능하지만, DB 전환을 전제로 설계
- 페이지, 데이터 모델, 관리자 기능을 모듈 단위로 분리
- 바이브코딩 중간에 기능이 추가되어도 쉽게 붙을 수 있게 설계
- 디자인도 하드코딩하지 말고 컴포넌트화
- 상담, 예약, 수업, 강사, 후기, 포트폴리오, 공지, 결제, 수강생 관리까지 확장 가능하게 설계

### 22.3 바이브코딩용 개발 철학

이 프로젝트는 처음부터 완벽한 기획서를 만들어놓고 그대로 구현하는 방식이 아니다. 개발하면서 이거 필요하네 싶은 기능을 계속 붙이는 방식이다.

원칙:

1. 기능은 작게 쪼갠다.
2. 데이터 구조는 넉넉하게 만든다.
3. 페이지는 컴포넌트 조립식으로 만든다.
4. 관리자에서 최대한 수정 가능하게 만든다.
5. 텍스트와 이미지는 하드코딩하지 않는다.
6. 디자인 시스템을 먼저 잡는다.
7. 사이트 공개 영역과 관리자 영역을 분리한다.
8. 나중에 DB, 로그인, 결제, 예약이 붙어도 구조가 무너지지 않게 한다.

### 22.4 추천 개발 순서

1. 프로젝트 뼈대: Next.js 프로젝트 생성, 라우팅 구조, 전역 레이아웃, 디자인 토큰, 공통 컴포넌트, mock data 폴더, 타입 정의
2. 공개 사이트 기본 화면: 홈, 수업 목록, 수업 상세, 강사진 목록, 강사 상세, 상담 신청, 오시는 길
3. 신뢰 요소 추가: 포트폴리오, 후기, 시설 / 장비, FAQ, 공지사항, 이벤트
4. 관리자 페이지: 대시보드, 상담 신청 목록, 수업 CRUD, 강사 CRUD, 후기 CRUD, 포트폴리오 CRUD, 공지 CRUD, 이벤트 CRUD
5. DB 연결: Supabase 또는 Prisma 기반 DB 연결, mock data를 실제 DB로 교체, 관리자 입력값이 공개 사이트에 반영되게 구성
6. 운영 기능: 예약 관리, 수강생 관리, 강사 관리, 과제 / 피드백, 출석, 결제, 알림톡

### 25.4 나중으로 미뤄도 되지만 구조는 열어둘 기능

- 수강생 로그인
- 강사 로그인
- 결제
- 출석
- 과제
- 피드백
- 알림톡
- 예약 캘린더

### 25.5 바이브코딩 중 주의할 점

- 한 파일에 다 넣지 않는다.
- UI 먼저 만들더라도 타입은 먼저 정의한다.
- mock data도 실제 DB처럼 구조화한다.
- 관리자에서 수정될 데이터와 고정 텍스트를 구분한다.
- 새로운 기능이 생기면 먼저 타입과 데이터 흐름부터 만든다.
- 디자인이 깨지지 않도록 공통 컴포넌트를 계속 재사용한다.

## 26. 결론

음악 학원 사이트의 핵심은 예쁜 홈페이지가 아니라 수강생이 믿고 문의하게 만드는 구조다.

처음에는 아래 구조로 가면 좋다.

- 홈에서 강한 첫인상
- 수업 페이지에서 내가 들을 수업을 명확히 이해
- 강사진 페이지에서 신뢰 형성
- 포트폴리오와 후기로 결과 증명
- 모든 페이지에서 상담 신청으로 연결

이후 운영이 안정되면 예약, 로그인, 과제, 결제, 수강생 관리 기능을 붙이면 된다.

## 27. 현재 구현 확정 사항

이 섹션은 실제 구현까지 완료되어 확정된 내용만 기록한다.
아이디어 단계였지만 구현하지 않았거나, 추후 변경 가능성이 큰 항목은 포함하지 않는다.

### 27.1 브랜드와 표현 정책

- 사이트명은 `서브컬처 · 게임 실용음악학원 OSUM`으로 사용한다.
- `/` 표기는 쓰지 않고 가운뎃점 `·`으로 구분한다.
- `아카데미`라는 단어는 사용하지 않는다.
- 타깃은 서브컬처, 게임음악, 애니메이션 BGM, J-POP, Sound Design 관심층이다.
- 외부 노출 문구에는 `씹덕` 같은 직접적 표현을 사용하지 않는다.
- `오타부` 표현은 쓰지 않고 `J-POP`으로 표기한다.
- `SFX` 대신 `Sound Design`으로 표기한다.
- OST 설명은 락, 오케스트라 등 특정 장르에 갇히지 않고 게임, 영화 음악까지 가능한 방향으로 설명한다.

### 27.2 현재 사이트 UI 방향

- 전체 색감은 밝고 활기차고 희망적인 톤을 유지한다.
- 첫 진입 시 OSUM 인트로 애니메이션이 재생된 뒤 사이트가 보인다.
- 상단 메뉴바는 스크롤 중 사라지고, 스크롤이 멈춘 뒤 페이드와 이동감 있게 다시 나타나는 방식으로 구현한다.
- 버튼 hover는 과한 리퀴드 글래스 효과를 사용하지 않는다.
- 색이 있는 버튼은 hover 시 버튼 색이 빠지고 텍스트가 파란색으로 변한다.
- 색이 없는 버튼은 hover 시 텍스트만 파란색으로 변한다.
- hover 전환 시간은 약 0.2초로 둔다.
- 모바일 UI는 하단 CTA와 카드 간격이 깨지지 않도록 정리된 반응형 구조를 사용한다.

### 27.3 포트폴리오 모달 UX

- 클래스와 강사 카드의 버튼명은 모두 `포트폴리오 보기`로 통일한다.
- 포트폴리오 목록 모달에서 카드를 누르면 상세 패널이 하단/중앙 기준으로 확장된다.
- 상세 패널은 좌측에 미디어, 우측에 제목, 설명, 장르/형식, 제작 포인트, CTA를 보여준다.
- 상세 패널이 열린 뒤에는 다른 포트폴리오 아이템을 좌측 리스트에서 빠르게 전환할 수 있다.
- 좌측 리스트 전환 시 사이버펑크/메트릭스 느낌의 텍스트 디코딩, 이미지 wipe 전환 효과를 사용한다.
- 목록으로 돌아갈 때는 배경을 깜빡이지 않고 확장 패널이 접히는 애니메이션을 사용한다.
- 확장 패널 닫기와 모달 닫기에도 별도 사라짐 애니메이션을 적용한다.
- 이미지 크기에 따라 상세 패널이 흔들리지 않도록 미디어 영역은 고정 비율 기반으로 유지한다.

### 27.4 CMS 포트폴리오 데이터 모델

포트폴리오 CMS 타입은 하나로 통합한다.
클래스용 CMS와 강사용 CMS를 따로 만들지 않는다.

하나의 포트폴리오 아이템은 다음 값을 가진다.

- 제목
- 장르
- 참여자
- 표시될 클래스
- 이미지 URL
- YouTube URL
- Audio URL
- 외부 링크
- 상세 설명
- 제작 포인트

장르는 노출 조건에 사용하지 않는다.
관리자가 직접 적는 표시용 텍스트로만 사용한다.

노출 조건은 다음 두 가지다.

- 참여자: 여러 강사를 중복 선택할 수 있다.
- 표시될 클래스: 여러 클래스를 중복 선택할 수 있다.

예를 들어 `조이고`라는 아이템에 참여자로 `김정환`, 표시 클래스로 `게임 · 영화 OST`를 선택하면, 이 아이템은 김정환 포트폴리오와 게임 · 영화 OST 포트폴리오 양쪽에 뜬다.
한 작품에 여러 강사가 참여할 수 있으므로 참여자는 다중 선택이어야 한다.
한 작품이 여러 수업과 연결될 수 있으므로 표시 클래스도 다중 선택이어야 한다.

### 27.5 CMS 저장 방식

- 브라우저별 캐시 저장소만 사용하는 방식은 확정 구조가 아니다.
- CMS 데이터는 서버 폴더의 `cms-data/portfolio.json` 파일에 저장한다.
- Vite 개발 서버에 `/api/portfolio` 로컬 API를 붙여 등록, 조회, 수정, 삭제를 처리한다.
- 인앱 브라우저와 크롬이 같은 로컬 서버를 보면 같은 CMS 데이터를 읽어야 한다.
- 서버 설정이 바뀌었을 때는 Vite 서버를 재시작해야 `/api/portfolio`가 동작한다.

### 27.6 관리자 페이지

- 관리자 페이지 주소는 `/admin`이다.
- 관리자 페이지에서 포트폴리오 아이템을 등록할 수 있다.
- 등록된 아이템은 관리자 목록에 다시 보여야 한다.
- 등록된 아이템은 수정할 수 있어야 한다.
- 등록된 아이템은 삭제할 수 있어야 한다.
- `프리뷰 종류`는 관리자가 직접 고르지 않는다.
- YouTube URL이 있으면 `Video`, Audio URL이 있으면 `Audio`, 둘 다 없으면 `Project`로 자동 판별한다.
- 제작 포인트는 쉼표로 구분해서 여러 개 입력하고, 확장 모달에서는 포인트 칩 형태로 표시한다.

### 27.7 미디어 프리뷰 정책

- YouTube URL이 있으면 확장 모달의 좌측 미디어 영역에서 YouTube iframe으로 재생한다.
- YouTube 임베드는 `youtube-nocookie.com/embed` 형식을 사용한다.
- YouTube URL 파싱은 다음 형태를 지원한다.
  - `https://www.youtube.com/watch?v=...`
  - `https://youtu.be/...`
  - `https://www.youtube.com/shorts/...`
  - `https://www.youtube.com/live/...`
  - `https://www.youtube.com/embed/...`
  - 영상 ID만 입력한 경우
  - `https://`를 생략한 경우
- Audio URL이 있으면 확장 모달에서 오디오 플레이어를 보여준다.
- YouTube URL과 Audio URL이 둘 다 없으면 이미지 프리뷰를 보여준다.
- YouTube iframe 재생을 기본으로 하므로 별도의 `YouTube에서 열기` 버튼은 사용하지 않는다.
